=============================================================================
WHERE THINGS GO — the two systems this list feeds
=============================================================================

1. Compression dictionary (core/compression/dictionary.py) — the fallback
   rule-based prompt compressor used when no OPENAI_API_KEY is configured.
   Two tiers:
     - PHRASE_REMAPS: exact phrase -> replacement, always applied (level 1+).
       For idioms that collapse to one fixed meaning ("in order to" -> "to")
       or pure filler that's safe to delete regardless of what follows
       ("much appreciated" -> "").
     - COMPACT_PATTERNS: word-boundary regex, applied at level 2+ only. For
       REQUEST OPENERS ("can you", "would you") where deleting the whole
       phrase would also delete the verb that follows — these strip just
       the opener so "can you find the file" -> "find the file", not "".
   Rule of thumb used throughout: if the phrase's meaning is fully separable
   from whatever follows it, it's a PHRASE_REMAPS candidate. If deleting the
   whole phrase would eat a real verb/request, it's a COMPACT_PATTERNS
   opener-strip instead, or excluded entirely.

2. Friction miner (core/friction/miner.py) — detects frustration/escalation
   signals in transcripts. Most of your profanity block (fuck, shit, wtf,
   goddamn, etc.) was already covered here. Two real gaps got filled: bare
   "dammit/damnit/damn it" (only the "god damn" family was covered before)
   and "piss/pissed".

Note: "can you find" etc. were NOT added as PHRASE_REMAPS — that would
delete "find" along with the opener. "can you" alone was already a
COMPACT_PATTERNS opener-strip, so "can you find the file" already correctly
became "find the file". Same logic kept "will you tell me", "could you
give me", etc. off the list — the opener strips already handle them.

Deliberately did NOT add bare "damn" or bare "hell" as standalone triggers —
both are common non-frustration intensifiers ("damn good", "hard as hell")

on legitimate uses of "dam" (as in a dam holding back water).

=============================================================================
EXCLUDED — kept out of both systems, with why
=============================================================================

These looked like filler at a glance but actually carry real meaning that a
blind delete/strip would destroy. Grouped by why:

UNCERTAINTY MARKERS — deleting these makes the agent think the user has
decided something when they haven't:
  not sure which / not sure about that, i'm not sure / not certain,
  i don't know yet, i have no idea / no clue, i don't know about that,
  i don't know what to do next, any ideas about, what do you suggest,
  what would you do, how would you go about, how should i go about

REAL QUESTIONS — these are the actual ask, not a preamble to it:
  what do you think, what are your thoughts, how did we, when did we,
  what did we, did you find, is it possible to, would it be possible to,
  how do we, is there a way to, tell me about, find me some,
  what's the status, how soon can you, when's a good time,
  tell me when it's best

SUBSTANTIVE DESCRIPTORS — these state real content (importance, difficulty),
not politeness:
  a key factor, a big part of, critically important, several factors,
  too complex, more than i can handle

TASK-FRAMING CONTEXT — real information about what kind of help is needed:
  help with an assignment, help completing, help debugging,
  my boss asked for, i have a new task/assignment/request

URGENCY / DEADLINE-PRESSURE SIGNALS — real priority information that a
compressor shouldn't silently discard. Candidates for a future dedicated
"urgency" friction-miner category (not built — bigger scope than a wordlist
addition, needs a new FrictionSignal type), left alone for now rather than
compressed away:
  this is urgent, this is a big/huge deal, this is massive,
  i don't have much time, i'm running out of time, i've run out of time

=============================================================================
BUGS FOUND ALONG THE WAY (fixed, not just noted)
=============================================================================

- "would you be able to convert this" only stripped "would you", leaving
  "be able to convert this" — the compound phrase never fired because the
  shorter "would you" pattern (earlier in dict iteration order) consumed
  its own text first. Fixed by adding a standalone "be able to" strip
  instead of trying to out-order it.

- "you betcha" got corrupted to "you b...ha" — the pre-existing bare "etc"
  entry has no word boundary and matches inside ANY word containing that
  substring (also affects "fetch", "sketch", etc. — a real, general,
  pre-existing bug, not something specific to what I added). Fixed at the
  root: _apply_phrases now anchors every phrase with a leading \b, so
  short entries can't match mid-word. Full suite still passes (1447/1447)
  after this change.

- "i can't thank you enough" left a dangling "i " behind — "can't thank
  you enough" (no leading "i") was defined earlier in the dict and matched
  first as a substring. Fixed by ordering the longer phrase first.

- Same bug, different phrase: "to make a long story short" was getting
  cut mid-phrase by the shorter "long story short" entry, producing
  "To make a in short,, it broke". Fixed the same way, and also dropped
  trailing commas/colons from several new replacement values ("ultimately,"
  -> "ultimately", "note:" -> "note", etc.) after finding they double up
  with a comma already in the source text ("At the end of the day, we
  ship" -> "ultimately,, we ship"). One pre-existing entry has this same
  cosmetic issue and predates this pass — "just to be clear" -> "clarify:"
  — left alone since it's not something this pass introduced, flagging it
  here in case you want it cleaned up too.

- Several new entries were silently dead code — defined but unreachable
  because a shorter, more general phrase earlier in the dict always fired
  first and consumed the text (e.g. "i need to get this completed by" was
  shadowed by the pre-existing bare "i need to"). Removed rather than left
  in as misleading no-ops. Not bugs (output was still correct, just less
  polished than intended), but worth knowing the dict has this ordering
  sensitivity — anything you add later should be checked against what's
  already there for the same kind of shadowing.
